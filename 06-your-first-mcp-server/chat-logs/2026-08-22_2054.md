## Step 6 — `src/server.py` (real debugging moment)

Initial version used `from mcp.server.fastmcp import FastMCP` — matches the
spec, but the background launch of `mcp dev src/server.py` **failed (exit
code 1)**. Diagnosed properly rather than guessed at: inspected the
installed `mcp` package's actual module structure (`pip show mcp` →
`mcp==2.0.0`; enumerated `mcp.server`'s submodules; found `mcpserver`, not
`fastmcp`), then confirmed via `mcp/cli/cli.py`'s own `_check_server_object`
function that `mcp dev` requires an `MCPServer` instance in this SDK
version. Conclusion: `FastMCP` was renamed to `MCPServer` between the SDK
version the spec assumed and `mcp==2.0.0`, actually installed on this
machine — same interface, decorator, and `.run()` default, different class
name. Fixed the import accordingly; the retry (`mcp dev src/server.py`)
then launched cleanly, which is itself strong evidence the fix was correct
(a wrong class name or missing `.tool()` method would have failed loudly
again). Framed to the user as a genuinely useful, realistic lesson — SDKs
drift from tutorials, check what's actually installed rather than trust
docs blindly — and flagged for a note in the README's "Known limitations."

One side incident during this debugging: a routine background-task
permission prompt in Claude Code got accidentally denied by a misclick; the
user said "please go ahead proceed" and it was retried successfully.
Separately, explained (twice, at increasing levels of detail) why Claude

## Side Q&A — how MCP actually works (before attempting the checkpoint quiz)

Before answering Step 9's checkpoint quiz, user paused to ask a batch of
conceptual questions about MCP itself — good instinct, understanding first
rather than guessing through a quiz. Answered one at a time as requested
(not dumped all at once), user acknowledging each with "yes"/"ok" to move
to the next.

1. **How MCP works + which server was used**: explained the core
   client-server model — a server exposes tools (and optionally resources/
   prompts) over JSON-RPC messages sent across a transport (stdio here); a
   client first asks "what can you do" (list tools), then sends "call this
   tool with these arguments" when relevant. Key clarification: the "MCP
   server" in this project isn't some third-party thing connected to —
   it's `06-your-first-mcp-server/src/server.py` itself, the code written
   in Step 6. The MCP Inspector was the **client** in all the testing done
   in Step 7, standing in for what would normally be Claude Desktop or
   another real client.
2. **Can a local MCP server be built and reused for other projects**:
   confirmed yes — that's exactly what Project 6 already is. Explained the
   general pattern (plain function → `@mcp.tool()` decorator → docstring
   as description → done) for adding more tools later, and sketched how to
   move from Inspector-only testing to actual daily use via Claude
   Desktop's config file (point it at the venv's `python.exe` + the path
   to `server.py`) — flagged that exact config syntax/path can vary by
   Claude Desktop version, so check its own settings rather than trust a
   path recited from memory.
3. **How the connection + multi-tool combination works**: broke down the
   handshake — client starts the server process, sends an "initialize"
   message, then "list tools"; the server responds with tool definitions
   built from the `@mcp.tool()` functions. For multiple servers, a client
   repeats that handshake with each one independently and pools all their
   tools into one combined menu internally, routing each call back to the
   right server when needed — explicitly tied back to the "Claude picks
   which tool fits" lesson from Projects 4/5, just scaled to tools coming
   from separate, independently-written server processes instead of one
   hand-assembled list.
4. **Why no API key is needed here**: explained that a key exists to
   identify a caller for billing/rate-limiting (why Anthropic's API needs
   one), while `dictionaryapi.dev` and MyMemory's free tier are public
   services with no billing model, controlling abuse via IP-based rate
   limits instead — a deliberate project choice (same reasoning as picking
   Open-Meteo in Project 5), not a workaround. Noted MyMemory's optional
   `email` param for a higher free-tier limit, unused here since this is a
   testing-scale project.
5. **Why `mcp dev src/server.py` specifically**: broken into its three
   parts — `mcp` (the CLI from the `mcp[cli]` extra), `dev` (the
   subcommand that specifically launches the MCP Inspector bridge — this
   is where the starlette/uvicorn dependencies from Step 1 actually get
   used), `src/server.py` (the file path). Contrasted with running
   `python src/server.py` directly, which would work per the file's own
   `mcp.run()` call but just sit silently on stdio with no UI to interact
   with it — `mcp dev` exists specifically to make that testable by a
   human.
6. **The "Sandbox (MCP Apps)" page at `http://127.0.0.1:6275/sandbox`**:
   answered carefully, flagging inference vs. certainty rather than
   guessing confidently. Certain: nothing in this project's own code
   creates it — `server.py`/`lookups.py` only return plain strings, no
   HTML/UI content. Inferred, based on the `mcp.server.apps` module
   surfaced during the Step 6 SDK-inspection debugging (names like `Apps`,
   `Extension`, `ResourceCsp`, `client_supports_apps`): likely a newer MCP
   protocol feature ("MCP Apps") letting a server return an interactive
   mini-UI sandboxed in an iframe as part of a tool result, which the
   Inspector spins up by default for any connected server regardless of
   whether that server actually uses the feature — probably empty/inert
   here since neither tool sends that kind of payload. Offered to give a
   precise answer instead of an inference if the user shares a screenshot,
   since the page only exists on their own machine and isn't reachable
   remotely.
