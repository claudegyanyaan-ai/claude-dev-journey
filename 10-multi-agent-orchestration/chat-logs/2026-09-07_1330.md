## Document verification before writing any pipeline code

Same discipline as Project 8: checked real extractability on all three
PDFs before assuming anything about them, rather than trusting file names.
`dwdm_osnr.pdf` turned out to be **byte-for-byte identical** (same MD5) to
Project 8's `osnr.pdf` — same known vector-graphics-not-real-text problem,
confirmed by rendering a sample page and comparing against `pypdf`'s
0-char extraction for that page. `ethernet.pdf` extracted cleanly.
`IP.pdf` had a low average chars/page but, unlike `dwdm_osnr.pdf`, every
page had *some* real text — confirmed by rendering a sample page (a real
Cisco slide deck) and pulling its exact extracted text back correctly.
This shaped the OCR-detection heuristic below: fraction of near-empty
*pages*, not average chars/page, since an average would have conflated
IP.pdf's genuine sparseness with dwdm_osnr.pdf's real extraction failure.

## Iteration 1 — `rag_core.py`: OCR auto-detection, extraction, chunking

- `needs_ocr()` — per-document heuristic: if a large fraction of a PDF's
  *pages* extract to near-nothing, treat the whole document as needing
  OCR. Verified against real numbers: `dwdm_osnr.pdf` had 33/40 pages
  return 0 chars (True), `IP.pdf` had 0/38 near-empty pages despite a low
  average (False), `ethernet.pdf` extracted cleanly (False).
- `extract_pages()` — branches to OCR (PyMuPDF render + Tesseract, reused
  from Project 8's `extract.py`) or plain `pypdf` extraction based on
  `needs_ocr()`, returning the same `{"page", "text"}` shape either way.
- `chunk_text()` — **deliberately not** Project 8's numbered-heading regex
  chunker. Checked all three real documents' actual structure first:
  `osnr.pdf`-style numbered headings ("1.3.2 ...") don't exist in
  `ethernet.pdf` (prose headings, no numbers) or `IP.pdf` (one slide title
  per page) — a heading regex would silently break on both. Replaced with
  a structure-agnostic fixed-size overlapping-window chunker that tracks
  page ranges per chunk for citation, working uniformly on all three.

Verified against all three real PDFs (not just "it ran"): correct
`needs_ocr` results, sane page/char counts, and a real, correctly-attached
first chunk from each document.

## Retrieval quality check — one false alarm, one real fix

Ran real domain queries through `retrieve()` before building anything on
top of it. `ethernet` and `dwdm_osnr` looked solid immediately. `ip`'s top
hits for "What does a router do?" looked weak by preview alone — but
digging into the *full* ranking (k=16) showed the actual router-definition
chunk was already in the original top-4, just with its relevant text
positioned past the 150-char preview cutoff. Lesson: a truncated preview
had made a working result look broken. Real issue found next: once
`ip`'s subagent was actually asked the same question, Claude's own answer
said the excerpt was "cut off" — the key sentence straddled a chunk
boundary because of the 800-char/150-overlap chunk size. Fixed by widening
`chunk_size` to 1200 and `overlap` to 300 and rebuilding all three
indexes (re-chunk + re-embed only, no OCR redo needed). Re-tested all
three subagents after the change: `ip`'s answer became complete, and
`dwdm_osnr`'s answer *improved* (went from "no explicit definition
found" to the full NF formula, quantum limit, and real-world ranges) —
confirming the wider window was a net improvement, not just a fix for one
case.

## Iteration 4 — orchestrator + full pipeline tracing

`orchestrator.py`: `classify_domain()` asks Claude itself (Haiku) which of
the three domains a query belongs to — a real agentic routing decision,
not keyword matching — then `route()` dispatches to the matching
subagent. `main.py`: a simple interactive loop over `route()`, each
question a fresh, independent call (no shared history across questions or
subagents — the actual "session/context management" concept this project
is about).

User asked how to actually verify, end to end, that orchestration ran,
which subagent got picked, and which document/pages it used — not
something the original design surfaced. Fixed properly rather than just
explaining it verbally: `answer_from_index()` now returns
`{"answer", "pages_referenced"}` (page numbers read directly from
`retrieve()`'s own chunk metadata, not from Claude's self-report),
threaded through the subagents and `orchestrator.route()`, which now
prints `[orchestrator routed to subagent: ...]`, `[document: ...]`, and
`[pages referenced: ...]` before every answer in both `orchestrator.py`
and `main.py`.
