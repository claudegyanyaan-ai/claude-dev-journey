## What "spec-writing" means (taught before first spec)

Explained the four ingredients of a spec good enough for an AI coding agent: scope it small (one command at a time — this is literally what "iterative refinement" means), state the exact interface/command syntax, state exactly where/how data is stored, and explicitly say what NOT to build yet (agents tend to over-deliver otherwise).

User was initially confused about what to even ask for, since the project folder was completely empty — clarified that "nothing set up yet" is a normal starting point for a spec; Claude Code creates files from scratch. Also had to explain, from first principles, *why* a CLI app needs a JSON file at all — each terminal invocation is a fresh process with no memory of the last one, so tasks must be persisted to disk (`tasks.json`) rather than kept only in a variable.

## Iteration 1 — `add` command

Sent a fully-worked example spec (mentor-provided, with each line's purpose explained, since this was the user's first-ever spec):
```
Create a new Python file at src/main.py for a command-line to-do app.
Right now, implement ONLY the "add" command: exact syntax, tasks.json format
{"task": "...", "done": false}, create the file if missing, confirmation
message. Explicit boundaries: don't implement list/done/remove yet, stdlib only.
```
Claude Code produced a clean `main.py` (`load_tasks`, `save_tasks`, `add_task`, `argparse` wiring) that respected every boundary. Reviewed together: why `load_tasks()` returns `[]` instead of crashing when `tasks.json` doesn't exist yet (avoids `FileNotFoundError` on first run), and traced `add_task()` line by line (read → append in memory → write whole list back → print confirmation — the same read-modify-write pattern used throughout the app). Accepted, ran `add "buy milk"`, confirmed `tasks.json` created correctly. Committed: `feat: add command for CLI to-do app`.

## Iteration 2 — `list` command

This time built the spec collaboratively via guided questions (first attempt at drafting solo led to a confused, off-topic answer — backed up and did it as a short Q&A instead): exact per-task line format (`1. [ ] buy milk` / `[x]` for done), and message for an empty list (`No tasks yet.`). Assembled spec together, sent it, reviewed the diff.

New concepts explained: `enumerate(tasks, start=1)` (yields index + item pairs, index starting at 1 — this is what produces the "1.", "2." numbering) and the one-line conditional `mark = "x" if task["done"] else " "`.

Debugging side-quest: user's terminal showed `(.venv)` even though this project has no virtual environment — root cause was the same terminal tab still had Project 1's `.venv` activated from earlier; `cd` into a new folder does not deactivate it. Fixed with `deactivate`. Harmless here (stdlib-only project) but flagged as a habit to watch.

Also walked through why a freshly-added task correctly showed `[ ]` not `[x]` (no `done` command exists yet to ever flip that field to `true` — not a bug). Ran `list`, confirmed output matched spec. The commit step for this iteration was skipped in the moment and its changes ended up folded into the next commit instead (see note below).

## Iteration 3 — `done` command

Built via guided Q&A: identify task by number, confirmation shows the task's full text (`Marked done: "wheat"`, not just the number), and an explicit error message for an out-of-range number. Assembled and sent the spec.

Claude Code's diff included a `mark_done()` function converting the 1-based display number to a 0-based list index (`index = number - 1`) with bounds checking `if index < 0 or index >= len(tasks)`. Reviewed together — this surfaced a genuine Python gotcha: Python lists support negative indexing, so without the `index < 0` check, `done 0` would silently succeed and mark the *last* task done via `tasks[-1]` instead of erroring — a real bug class (upper-bound-only checks missing the negative case). Also covered `type=int` in `argparse`, which auto-validates and rejects non-numeric input before the function is ever called.

Tested: `done 2` (worked, marked "wheat" done), `done 99` (correctly refused), `list` (confirmed `[x]` now showing). Committed as `feat: done command for CLI to-do app` — this commit's `git add .` also picked up the still-uncommitted `list` changes from Iteration 2, so `list` ended up bundled into this commit instead of having its own history entry. Not lost work, just messier history — flagged as a lesson: check `git status` right before committing so you know exactly what's about to be bundled together.

## Iteration 4 — `remove` command

Given the established pattern, mentor proposed the spec directly (mirroring `done`'s shape: delete by number, confirmation with task text, error on invalid number) rather than another full Q&A round, for pace. User accepted the diff without a joint review this time (first deviation from the review-before-accept habit) — mentor let it pass this once given how closely it mirrored `done`, but flagged the norm should hold going forward. Verified correctness via testing instead: `remove 3` (deleted a duplicate "buy milk" left over from earlier experimentation), `remove 99` (correctly refused), `list` (confirmed exactly 2 real tasks remained). Committed: `feat: remove command for CLI to-do app`.
