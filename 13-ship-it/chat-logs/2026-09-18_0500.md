# Project 13, Part 1 -- Cost & Rate Limits -- Session Log (2026-09-17 to 2026-09-18)

## What got built
- `rate_limit.py`: `check_rate_limit(username)` -- raises HTTP 429 once a user
  has made 10 `/ask` calls since midnight UTC. Checked BEFORE calling Claude.
- `usage.py`: `log_usage(...)` -- records real `response.usage` token counts
  and an estimated cost (Haiku 4.5 pricing: $1/MTok in, $5/MTok out).
- `db.py`: new `usage_log` table, doubling as the cost ledger and the rate
  limiter's source of truth.
- `rag/answer.py`: accumulates real token usage across every Claude call a
  question triggers (multi-round tool use), returns it to the caller.
- `main.py`'s `/ask` route: checks the limit, calls the orchestrator, logs
  real usage, returns `requests_remaining_today`.

## What went wrong, and how it got fixed
1. Wrong venv activated first (Project 1's, not Project 12's) -- each
   project needs its own venv; none existed yet for Project 12 on this
   Windows machine since `.venv` is gitignored and never travels via git.
2. `psycopg2.OperationalError: could not translate host name ...` running
   `python db.py` -- root-caused via `nslookup` to the local ISP/router's
   DNS silently refusing to resolve the Neon pooler hostname specifically
   (`Query refused`), while general internet access and even Neon's own
   website worked fine. Confirmed by querying Google's DNS (`8.8.8.8`)
   directly, which resolved it correctly. Fixed by switching the machine's
   DNS servers to `8.8.8.8` / `8.8.4.4`.
3. A multi-line `python -c "..."` command hung indefinitely in PowerShell
   (quoting/continuation-prompt issue) -- switched to writing a real `.py`
   script file via a PowerShell here-string (`@'...'@`) instead, which
   avoided the quoting problem entirely.

## Verification
- `python db.py` created `usage_log` successfully after the DNS fix.
- Ran the backend locally (`uvicorn main:app`), signed up a test user
  (`ratetest1`), and fired 11 `/ask` requests in a loop:
  - Requests 1-10 succeeded, `requests_remaining_today` counted down 9->0.
  - Request 11 was blocked with `429 Daily limit of 10 questions reached.`
- Queried `usage_log` directly: all 10 rows had real, non-zero
  `input_tokens`/`output_tokens` (~2841 in / 250-360 out per question) and
  a real `estimated_cost_usd` (~$0.0044-0.0046 each) -- confirming the
  logging measures actual API usage, not an estimate.
- Committed (`a1c1ec5`) and pushed; Render auto-redeployed cleanly (41.2s,
  confirmed via the Render dashboard).

## Close-out
Self-assessed confidence: 3.5/5. Conceptual questions covered (answered by
the mentor, not walked through live this round):
1. Rate limit checked before calling Claude -> a blocked request costs $0,
   same principle as Project 11's "gate before the expensive/irreversible
   step" eval hook.
2. `usage_log` backs both the ledger and the rate-limit count so there's a
   single source of truth, instead of a separate counter that could drift
   out of sync with the log.
3. Calendar-day-UTC reset downside: doesn't align with a user's local day
   (e.g. resets at 5:30 AM IST, not midnight IST), and a user straddling
   the UTC midnight boundary could get 20 questions in a few minutes.
