The spec itself is thorough: goal (answer questions from `osnr.pdf` only,
citing sections), document notes (40 pages, 6 chapters, consistent numbered
headings like `1.1`/`2.3`, recurring callout patterns, tables/equations that
must stay attached to their paragraph, a known PDF-extraction artifact of
duplicated back-to-back headings), and four **design choices made by the user
up front, not left to Claude Code to invent**:

1. **Chunking by the document's own numbered section headings** (regex on
   lines like `^\d+(\.\d+)*\s+\S`), not fixed-size blocks — keeps each chunk
   a complete unit instead of cutting a table or equation in half. Each
   chunk carries chapter, section, heading, and page-range metadata for
   citations.
2. **Embeddings via local `sentence-transformers`, model
   `all-MiniLM-L6-v2`** — small, fast, no API key, sized for one 40-page
   document, explicitly not a general recommendation for every future
   project.
3. **In-memory storage/retrieval, no vector database** — a JSON file of
   chunks + a NumPy array of embeddings, cosine similarity computed in
   memory, simpler than standing up Chroma/FAISS at this scale (50–150
   chunks expected).
4. **Indexing and querying kept as two separate scripts**, not one —
   building the index is slow and one-time, answering is fast and repeated;
   explicitly named as the same underlying reason as the fetch/format split
   in Project 6.

Grounding/citation behavior is enforced entirely through the prompt sent to
Claude at query time: answer only from the top-k retrieved chunks (k=4 to
start), cite the section/heading, and say plainly if the excerpts don't
contain the answer rather than falling back to general knowledge.

## Step 2 — `extract.py`: the PDF's text layer turned out mostly missing

Built `extract.py` around `pypdf` per the spec, ran it against
`docs/osnr.pdf`: 40 pages extracted, but only **6,415 total characters** —
roughly 5-8% of what a real 40-page technical document should contain.
Cross-checked with two more independent libraries (`pdfplumber`, `PyMuPDF`)
— all three agreed, and none could find **Section 1.3.2 / the quantum-limit
noise figure content the spec's own verification demo depends on**
anywhere in extractable text. Rendered a "blank" page to a PNG and looked
at it directly (via `PyMuPDF` + the `Read` tool's image support): the page
was visually packed with a real table, a worked "Interactive Exercise," and
the literal sentence *"3 dB, which corresponds to the quantum limit for
phase-insensitive amplification"* — none of which any extractor could see.
Conclusion, well-evidenced rather than assumed: most of this PDF's body
text is embedded as vector graphics/outlined shapes, not real selectable
characters — a genuine content problem, not a library choice or a bug to
code around.

Stopped and flagged this plainly rather than silently working around it.
Presented four options via `AskUserQuestion`; user picked **"OCR via my
vision"** (Claude transcribes rendered pages directly) initially, but then
interrupted the very next tool call (a `claude-api` skill lookup) to say
explicitly: **"go ahead & use the OCR-based ... don't want to go for paid
api base version"** — overriding the earlier choice once the cost
implication was concrete. Switched to **local Tesseract OCR** instead:
installed via `winget install UB-Mannheim.TesseractOCR` (not already
present), rebuilt `extract.py` around `PyMuPDF` (page → image) +
`pytesseract` (image → text), with a fallback to Tesseract's default
Windows install path since a fresh install isn't reliably on `PATH` within
the same session. Result: **68,715 characters recovered (~11x more)**,
all 6 chapters present, Section 1.3.2 recovered correctly and verified by
direct OCR spot-check of the surrounding pages. `pypdf` and diagnostic-only
`pdfplumber`/`pdfminer.six` were uninstalled again once OCR was confirmed
working; `requirements.txt` re-frozen to the real dependency set
(`pymupdf`, `pytesseract`, `Pillow`, no `pypdf`).

## Between steps — user's own follow-up check on 1.2/1.2.1/1.2.2/1.2.3

Before moving to `chunk.py`, user asked Claude Code to specifically verify
whether Section 1.2's subsections had actually been OCR'd (just maybe not
matching the diagnostic regex used to scan for headings) or were genuinely
lost/merged into 1.1.2's chunk. Direct investigation (not assumption)
confirmed the content was present but disguised by **three distinct OCR
artifacts** on the heading line itself: a stray `"- "` dash prefix
(`"- 1.2 Physics..."`), a stray `". "` period prefix (`". 2.2 EDFA..."`),
and one heading that lost its leading chapter digit entirely (`"1.2.3"`
read as `".2.3"`). Tested whether bumping OCR DPI (300/400 vs. 200) reduced
these — it didn't, confirming this isn't a resolution issue and no point
spending extra OCR time on it. This directly shaped `chunk.py`'s design
before it was even written.

## Step 3 — `chunk.py` + tests: a bug caught by real-data testing, twice

Built the heading-boundary chunker with regex tolerance for the three OCR
artifacts above, plus the spec's noted duplicate-heading collapsing. Wrote
14 hand-crafted unit tests first (`tests/test_chunk.py`) — all passed. But
running it against the **real** OCR'd document turned up two real bugs the
synthetic tests hadn't caught:

1. The junk-prefix regex was *too* loose — a bare leading period
   (`[-.•*\s]{0,3}`) matched both the genuine `". 2.2"` prefix case *and*
   the dropped-leading-digit case (`".2.3"`), silently mislabeling
   `1.2.3` as section `2.3`. Fixed by requiring a period-prefix to be
   followed by whitespace, which is exactly what distinguishes the two
   cases.
2. Section 6.5.2 in the real document had **both its heading and its
   opening sentence duplicated** back-to-back (not just the heading, as
   elsewhere) — the original collapse logic only handled a bare repeated
   heading with zero accumulated body text, so it produced one useless
   74-char "stub" chunk next to the real 482-char one. Generalized the fix:
   any exact repeat of the same section+heading with no *other* heading in
   between now gets merged, regardless of how much short content
   accumulated first. Added a test matching this real shape, and adjusted
   the old synthetic "non-adjacent repeat" test to check what's actually
   distinguishable — a genuinely different heading interrupting the two
   occurrences.

Final result against the real document: **119 chunks** across all 6
chapters, 14/14 tests passing. Also flagged (not fixed here, deferred to
Step 4): 22 of the 119 chunks are empty or near-empty — parent headings
(e.g. `2.4`) that go straight into their first subsection with no intro
text of their own. Real document structure, not a bug, but nothing worth
embedding.

## Step 4 — `build_index.py`: ran clean, index verified byte-for-byte

Wired extract → chunk → filter (dropped the 22 near-empty chunks, matching
Step 3's flag) → embed (`sentence-transformers`, `all-MiniLM-L6-v2`) →
save. Ran it for real: 60s OCR, **97 chunks kept**, 384-dim embeddings,
saved to `data/index/chunks.json` + `embeddings.npy` + `meta.json`.
Cross-verified the saved files directly rather than trusting the script's
own printout — chunk count matches embedding array shape, Section 1.3.2 is
present in the saved index with the correct text and `pages: [2, 3]`, and
embeddings come out L2-normalized (norm 1.0). Each chunk is embedded as
`"Section {n} — {heading}\n{text}"` rather than raw body text alone, so a
query echoing heading wording matches as well as one echoing body phrasing.

## Step 5 — `retrieve.py`: clean separation between relevant and not

Loads the index, re-normalizes embeddings defensively at load time (rather
than trusting they're already unit-length), embeds the query, returns
top-k by cosine similarity (dot product, since both sides are unit-length).
Tested against the quantum-limit question: **Section 1.3.2 came back as
the #1 hit (score 0.653)**, followed by three other legitimately related
noise-figure sections from later chapters. Tested an unrelated question
("chocolate chip cookie recipe") for contrast: best score only **0.095** —
a wide, clean gap that bodes well for Step 6's grounding behavior. Fixed a
minor cosmetic bug while testing: an em-dash in the sanity-check print
output rendered as `�` in this Windows console (a codepage mismatch, not a
data issue) — swapped to a plain hyphen.
