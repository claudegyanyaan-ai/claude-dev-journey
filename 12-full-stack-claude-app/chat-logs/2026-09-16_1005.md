## Dockerizing the backend for Render

Render's native Python buildpack has no way to install an OS-level
package, and `pytesseract` (already a dependency, used for OCR-based PDF
ingestion) shells out to the `tesseract-ocr` binary. Fix: switched the
Render service to a Docker-runtime deploy instead of the native runtime,
adding `backend/Dockerfile` (Python 3.14-slim base, matching the local
`.venv`; installs `tesseract-ocr` via `apt-get`; copies
`requirements.txt` and installs it before the rest of the source, so
Docker can cache that slow layer; shell-form `CMD` specifically so
Render's injected `$PORT` gets expanded by the shell before `uvicorn`
sees it) plus a `.dockerignore`. Also gitignored `.DS_Store` and deduped
`requirements.txt` while in there.

## The Render deploy OOM-killed itself -- twice

First deploy attempt crashed the instance outright. Diagnosis: `main.py`
imports the RAG pipeline at module level, which imports
`sentence_transformers` (and its dependency, `torch`) at module level too
-- so the full memory cost of loading that library was being paid at
every process startup, before `uvicorn` even bound to a port. On a
Render free-tier instance (512MB), that alone was enough to OOM-kill the
process before it ever became reachable.

**First fix, insufficient**: moved the `sentence_transformers` import
from module level into `embed_text()` itself, so the cost is deferred to
the first actual embedding call instead of every startup. This let the
process start and bind to a port successfully -- but the very first real
`/ask` request (which triggers the first embedding call) still OOM-killed
the instance. Deferring the import only moved *when* the memory got
spent, not *how much* -- loading torch and running even one CPU inference
was still too much for 512MB.

**Real fix**: swapped `sentence-transformers` out for `fastembed`, which
runs the identical model (`sentence-transformers/all-MiniLM-L6-v2`, same
384-dimension output) through ONNX Runtime instead of PyTorch. Same
embeddings, far less memory. No re-ingestion of already-uploaded documents
needed, since the underlying model weights and output vectors are
unchanged -- only the runtime executing them changed.

## Verifying the fix without exact numbers

Render's free tier doesn't expose memory/CPU metrics at all ("Upgrade to
any paid compute plan to view application metrics like memory and CPU
usage"), so the exact headroom `fastembed` leaves couldn't be measured
directly. Treated the absence of a crash as the real signal instead: an
`/ask` request completed successfully end-to-end with no OOM event,
unlike the `sentence-transformers` attempt, which crashed the instance
outright under the identical request. Good enough to move on without
chasing an exact figure.

Backend now live at `https://docs-assistant-szza.onrender.com` (Render
service "Docs Assistant", Docker runtime, Singapore region).

## Deploying the frontend to Vercel

Hit a false alarm first: the copy of the frontend under this chat's
upload folder was missing `package.json`, `lib/auth.ts`, `lib/topics.ts`,
`components/UploadModal.tsx`, and the rest of the Next.js scaffold --
only three source files had ever been uploaded to the chat itself. Rather
than guess at rebuilding those files blind, checked the actual project on
the user's linked machine and confirmed the real, complete frontend
(Next.js 16.3.5, already pushed to the `claude-dev-journey` GitHub repo)
was there the whole time -- the uploaded copy was just a partial snapshot
from earlier in the chat, not the real state of the project.

Asked the user to choose between the Vercel CLI (driven from this
session) or the Vercel dashboard (driven by the user) for the actual
import step, since it needs an interactive login either way -- user chose
the dashboard. Because `claude-dev-journey` is one shared monorepo rather
than one repo per project, the Vercel project import needed its **Root
Directory** set explicitly to `12-full-stack-claude-app/frontend` (not
the repo root) for Vercel to find the Next.js app at all, plus
`NEXT_PUBLIC_API_URL` set to the Render backend URL above as a build-time
environment variable. Deployed successfully to
`https://docsassistant.vercel.app`.

## Tightening CORS

`backend/main.py`'s `CORSMiddleware` had shipped with `allow_origins=["*"]`
and a comment flagging it as temporary ("tighten ... once we deploy").
With both halves now actually live, narrowed it to
`["https://docsassistant.vercel.app", "http://localhost:3000"]` --
keeping local dev working alongside the real deployed origin instead of
leaving it wide open. Committed (`bd0ee65`) and pushed.

Side note worth remembering: this session's own sandboxed device shell
has no cached GitHub credentials (no `credential.helper`, no `gh` CLI) --
the commit could be made there, but the push had to be run by the user
from their own Terminal/VS Code, same as any git operation needing auth
that a sandboxed shell doesn't have. Render auto-redeployed on the push.
