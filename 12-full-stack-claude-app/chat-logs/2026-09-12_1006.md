  `sentence-transformers`, `pymupdf`, `pytesseract`, `pypdf`, `numpy` —
  the RAG-related packages (`sentence-transformers`, `pymupdf`,

- **`.env.example`**: `DATABASE_URL`, `ANTHROPIC_API_KEY`, `JWT_SECRET` —
  placeholders only, no real values.
- **`db.py`**: loads `DATABASE_URL` via `python-dotenv`, opens one
  module-level `psycopg2` connection, and defines `create_tables()`
  which creates three tables with `CREATE TABLE IF NOT EXISTS` (safe to
  rerun):
  - `users` (id, unique `username`, `password_hash`)
  - `documents` (id, `topic` restricted by a `CHECK` constraint to
    `'dwdm_osnr'`/`'ethernet'`/`'ip'`/`'others'`, `filename`,
    `uploaded_at` defaulting to `NOW()`)
  - `chunks` (id, `document_id` as a foreign key to `documents.id`,
    `page_number`, `chunk_text`, `embedding` typed `JSON`)

  A `__main__` block calls `create_tables()` and prints a confirmation, so
  the file doubles as a one-off setup script (`python db.py`). Verified
  with `python3 -m py_compile db.py` (syntax only — no real `DATABASE_URL`
  is configured yet, so an actual connection wasn't attempted this
  session).

## Explanation given: embedding-as-JSON vs. pgvector

Walked through why `chunks.embedding` is a plain `JSON` column rather than
using the `pgvector` Postgres extension: `pgvector` stores vectors
natively and supports indexed similarity search inside SQL, which pays
off at large scale (millions of rows). At this project's actual scale — a
handful of PDFs, low thousands of chunks — loading all embeddings into
Python and computing cosine similarity by hand (same approach as Projects
8/10's in-memory retrieval) is fast enough and avoids installing/
configuring an extra Postgres extension for a problem that doesn't exist
yet. JSON here is only for persistence across restarts; the actual
similarity math still happens in Python, not SQL. Framed explicitly as a
deliberate, revisitable tradeoff (migrate to `pgvector` if/when the corpus
ever grows enough to need indexed search), not an oversight.

Also covered while explaining `db.py`: the foreign key on
`chunks.document_id` (Postgres enforces that a chunk can't reference a
nonexistent document, and blocks deleting a document that still has
chunks) and the `CHECK` constraint on `documents.topic` (pushes topic
validation into the database itself rather than relying on application
code alone to keep it correct) — both new patterns versus earlier
projects' plain scripts/Excel storage.
