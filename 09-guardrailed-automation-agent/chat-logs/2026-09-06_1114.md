## Iteration 1 — `extract.py`

Rebuilt from the locked design rather than guessing at the lost draft:
system prompt requiring every field copied verbatim (never inferred), a
JSON object with exactly `name`/`age`/`course_name`/`contact`/`email`,
empty string for anything not literally stated. Same shape as Project 3's
extraction pattern, checked directly against `03-structured-data-extractor/
src/main.py` for consistency rather than reinventing the pattern.

**Debugging detour — a fake 401.** First live test against the three real
sample emails returned `AuthenticationError: Unauthorized` from every one.
Chased this for real: verified the key's structure locally (correct
`sk-ant-api03-` prefix, right length, no stray whitespace), confirmed on
`platform.claude.com` that the key was active with a real balance and
payment method attached, byte-for-byte compared the key across two
re-pastes (identical both times) — all of it pointed at a valid, working
key. The actual cause: the sandboxed shell being used to run the test had
its own network proxy silently intercepting requests to
`api.anthropic.com` and returning a **plain-text** `401 Unauthorized`
before the request ever reached Anthropic — distinguishable from a real
Anthropic auth error, which always comes back as JSON with a
`type: authentication_error` body. Confirmed by hitting the real API
directly from a different environment and seeing the real JSON error
shape for a deliberately-bad key. Worth remembering as a debugging
instinct: an unexpected error's *shape*, not just its status code, can be
the tell that it isn't coming from the service you think it is.

**Real bug caught once the network issue was worked around:** 2 of the 3
real sample emails came back wrapped in ` ```json ... ``` ` fences despite
the system prompt explicitly saying not to. Fixed with a
`_strip_code_fence()` helper in `parse_response()` — stripping fence
markers defensively before `json.loads()`, rather than trying to get
Haiku to 100% prompt compliance. `missing_age_01.txt` correctly extracted
`age: ""` (never a guess), `implausible_age_01.txt` correctly extracted
`age: "5"` verbatim (rejecting it isn't extraction's job — that's
guardrail's). 7 unit tests added for `parse_response()`, including the
fence-stripping case built from the real failure observed.

## Iteration 2 — `guardrail.py`

Pure decision logic, no network or file I/O: `missing_fields()`,
`is_age_plausible()` (10–100 — a judgment call the original spec didn't
pin a number to, called out directly rather than picked silently),
`is_email_well_formed()` (regex), `find_duplicate_email()` (case-
insensitive, takes existing rows as a plain list of dicts rather than
reading a spreadsheet itself — the whole reason it's independently
testable). `evaluate()` combines all four into one `{decision, reasons}`
result, with reasons designed to avoid redundant/confusing pairs (a
missing age doesn't also report "not plausible"; a malformed email skips
the duplicate check entirely). 15 unit tests, including the two real
extracted leads from Iteration 1 (age 5, missing age) as concrete
regression cases rather than only synthetic ones.

## Iteration 3 — `store.py`

Safe append-only Excel I/O. Neither the checkpoint nor the root planning
docs specified where the spreadsheet should live or what its schema should
be — nothing existed yet — so picked `data/enrollments.xlsx`, one
`"Enrollments"` sheet, columns in `guardrail.FIELDS` order (imported, not
redefined, as the single source of truth). Flagged as an assumption rather
than presented as a given.

**Real bug, caught only on the user's actual machine:** all 9 local tests
passed in the (Linux) build environment, but running the same suite on
Windows produced 5 `PermissionError`s during `tempfile.TemporaryDirectory`
cleanup — `openpyxl`'s `read_only=True` mode keeps its underlying zip file
handle open until `.close()` is called explicitly. Linux doesn't care about
deleting a file with an open handle; Windows refuses. A genuine
platform-specific gap the Linux-only build side could never have caught on
its own — fixed with explicit `try/finally: wb.close()` in both
`load_rows()` and `append_row()`, then re-verified clean on Windows.

## Iteration 4 — `agent.py`

The CLI tying `extract → guardrail → store` together: prints what got
extracted, auto-writes when `guardrail.evaluate()` says it's safe,
otherwise shows the reason(s) and asks `Write this row anyway? [y/N]`
(defaulting to No on a blank answer or EOF — same "never act on an
uncertain case" discipline as the rest of the pipeline). Accepts multiple
email files in one run and reports a written/total summary at the end.
8 new tests mock the one network call (`extract.extract_from_file`) and
drive the real `guardrail`/`store` logic underneath, including a
duplicate-across-runs scenario. 39 tests total, all passing.

**Two more real-world snags on the actual first live run** (both expected
behavior, not bugs): re-running `clean_01.txt` correctly flagged a
duplicate against a row from earlier manual testing, and confirming `y` at
the prompt hit a `PermissionError` writing to `enrollments.xlsx` — because
the spreadsheet was open in Excel at the time. Windows locks files that
are open in another program; closing Excel and re-running wrote cleanly.
Good, concrete example of the difference between a code bug and ordinary
OS-level file locking.
