## Building the gating hook

Recapped `PreToolUse` vs `PostToolUse` (the user's existing
`post-commit-push-reminder.sh` fires *after* a commit and can only react;
gating a commit requires intercepting it *before*). Confirmed current
Claude Code hook semantics via docs (exit code 2 blocks unconditionally;
`if: "Bash(git commit *)"` scopes a handler to matching commands) before
writing anything, since this project's whole point is not trusting a
self-report.

Built `check-eval-before-commit.sh`: ignores anything that isn't a
`git commit`, otherwise reruns `run_eval.py` fresh via the Project 10
venv's Python, parses the `=== N/M passed ===` summary line, and blocks
(exit 2) below a 100% threshold — or if the eval script itself fails to
run at all (missing API key, etc.), treating "can't verify" as "block,"
not "allow." Wired into `.claude/settings.json` as a new `PreToolUse`
entry alongside the existing `PostToolUse` reminder hook.

## The hook didn't actually fire — and why that's not a bug

The third commit (adding the hook itself) went through instantly with no
`Eval gate: ...` message anywhere — easy to misread as "it works." It
doesn't, for a specific reason worth remembering: Claude Code's
`PreToolUse` hooks only intercept tool calls **Claude Code's own agent**
makes through its Bash tool. They have zero visibility into a `git
commit` typed directly into a terminal by a human, which is exactly what
happened here. That's a real, permanent scope limit — a genuine git-level
`.git/hooks/pre-commit` script would be the tool for gating *every*
commit regardless of who runs it, and is a different mechanism entirely.

User declined to run the "real" test (asking their own VS Code Claude
Code session to make a commit and watch it get blocked). As a lighter
alternative, verified the script's own logic remotely by piping it
simulated Claude Code stdin directly:
- a non-`git commit` command → correctly ignored, exit 0.
- a `git commit` command → correctly found the venv Python at the right
  path, attempted to run the eval, and — since this ran from a Linux
  sandbox rather than the user's actual Windows machine, so the venv's
  `python.exe` can't execute there (`Exec format error`) — correctly
  **blocked** with a clear reason, exercising the "can't verify, so
  block" fail-closed path.

This confirms command filtering, path resolution, and the failure-path
blocking all work. The one thing still unverified is the success path (a
real 15/15 run producing `Eval gate: 15/15 passed (100%) -- commit
allowed.`) — that needs an actual Claude-Code-driven commit on the user's
machine, which is a carried-over open item, not assumed to work.
